# デザインシステム移行ワークフロー

このリポジトリ専用。機能の完了とデザイン移行の完了を区別する。

## 参照先と正本

- [移行計画](../../../plans/design-system-adoption-plan.md): 優先順位、対象、受け入れ条件。
- [進捗ノート](../../../docs/design/design-system/PROGRESS.md): 画面・部品ごとの状態と証跡。
- [機能仕様](../../../specs/multi-vendor-ecommerce/00-overview.md): 変更に関連する要件・インターフェース・ワークフロー・品質・テスト仕様を読む。
- [文書配置・同期ガイド](../../../.claude/steering/documentation-guide.md): 文書ごとの役割。
- [QA_HANDOFF](../../../docs/testing/QA_HANDOFF.md): 全体テスト統計の正本。

## 1. 計画を保存してから実装する

1. 依頼と既存仕様、呼び出し元、表示状態を確認する。既存の移行計画と進捗ノートから対象IDを選ぶ。
2. 実装前に `plans/` へ、対象ID・変更内容・対象外・依存関係・受け入れ条件・先行テスト・実装後チェック・更新する文書を保存する。既存計画が十分なら対象項目を明示して再利用する。
3. ユーザーの既存承認は再利用する。新たな高影響の仕様判断や範囲拡張だけ確認する。
4. 進捗を「対応中」にする。新規対象には台帳の既存IDを変更せず、新しい連番IDを割り当てる。

## 2. TDDで変更する

- **Red**: 新要件・不具合を検証するテストを先に追加し、期待した理由で失敗したことを確認・記録する。環境エラーをRed実績にしない。
- **Green**: 要件を満たす最小限の実装で通す。
- **Refactor**: 共通化・整理後に関連テストを再実行する。
- 表示・余白・色・focus・狭い画面はブラウザーテスト、操作・状態遷移は適切なRTL等のテストを使う。CSSの文字列をなぞるだけのテストは追加しない。
- 既に実装済みの対象への回帰テストは「既存実装の回帰確認」と記録し、過去のRedを創作しない。
- 文書だけの変更ではTDDを適用せず、文書検証を実施する。

## 3. 実装後に検証する

- 関連テスト、`bun run lint`、`bunx tsc --noEmit` を実施する。Refactor後の最終結果を記録する。
- PC（1440px）・モバイル（390px）を基本とし、境界の幅も必要に応じ確認する。横スクロール、折り返し、表示状態、キーボード操作、focus、見出し、コントラストを確認する。
- Playwright・axe等で確認し、通常・空・エラー・送信中・成功など対象で必要な状態を受け入れ条件に照らす。ダッシュボードはライト・ダークを確認する。
- 第三者UI、認証後、決済など実検証できない範囲は理由と解除条件を残す。外部送信・購入・DB初期化を検証のためだけに実行しない。
- 失敗・未実施の必須チェックがあれば「検証済み」にしない。環境制約で止まった対象は「保留」にし、実装の有無も残す。

## 4. 仕様と進捗を同期する

実装したセッション内で、次の確認・更新を行う。

1. 進捗ノートに日付、ID、変更概要、Red/Green/Refactor、コマンド・結果、確認した画面と状態、制約を記録する。未コミットならその旨を書く。
2. 関連する `specs/multi-vendor-ecommerce/` と `docs/design/` の要件・設計・タスク・進捗を確認し、影響する文書を更新する。純粋な装飾変更等で仕様変更がない場合は、対象文書のリンクと「変更不要」の理由を残す。
3. 移行計画の対応するチェック項目を同期する。部品チェックは実装だけで完了にせず、検証と文書同期が揃ったときにチェックする。
4. テスト追加・変更時は既存の文書同期ルールに従いQA_HANDOFFの課題と引き継ぎも更新する。全体統計・カバレッジは実測した場合だけ正本から同期し、部分実行を全体値へ足し込まない。
5. フェーズ完了時は `docs/PROGRESS.md` に新ノートへの参照と概要を追記する。既存の機能完了履歴は維持する。
6. 検証・文書同期が揃った項目だけ「検証済み」にする。残課題がある場合は別IDで明示し、対象全体の完了に含めない。

## 完了判定

- 保存した計画の受け入れ条件と必要なテスト・表示確認が通っている。
- 関連仕様書の更新または変更不要の根拠、計画のチェック、進捗ノートの証跡が揃っている。
- 最終報告に変更内容、検証結果、未解決事項と文書リンクを含める。
- コミットは明示的な依頼がある場合だけ行う。未コミットでも文書同期を省略しない。
