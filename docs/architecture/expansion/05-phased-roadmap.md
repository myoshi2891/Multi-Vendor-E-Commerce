## 2. 順序の根拠

- **Phase 0 → A**: セキュリティ・正確性の穴の上に構造改修を積まない（Round 1 勧告の維持）
- **A → B**: ファセット検索（③）は属性（②）が、属性はカテゴリツリー（①）が前提という依存の鎖
  （[02 §3](02-current-state.md)）。逆順で作ると手戻りが確定する
- **C は A と並行可能**: 出品審査（④）はカテゴリ構造に依存しないため、Phase A と並走できる。
  C 内は ⑨（通知）を先頭に置く — ④⑥の通知要件の共通前提であり、先に確定させると
  各ワークフローの通知定義が単純化する。取引後の鎖は
  「チケット（DIRECTION-03）→ RMA（⑥）→ 返金実行（DIRECTION-01）→ restock（012）」の順で接続
- **⑦ → ⑩ の順**: レビュー評価集計の修正がセラー指標のシグナル1系統を供給する
- **D は最後**: レコメンド（⑤）の効果はカタログの構造化（A）と回遊導線（B）の質に比例する。
  販促（⑧）も集客・転換のレバーとして同格。ただし ⑤ の「共起注文 SQL」だけは独立に PoC 可能

### 着手形態の注意（spike と実装の二段構え）

柱①〜⑩の spike（設計調査）は**読み取り調査 + 設計文書のみ**のため、Phase 0 と並行して
着手できる。ただし各 spike の**後続実装プラン**（スキーマ変更・クエリ変更を含む）は
Phase 0（001〜006）完了後の実行を推奨する。①②④⑥⑦⑧⑩の実装はスキーマ変更を含むため、
実装プラン作成時に相互のマイグレーション順序を明記すること。

## 3. ブランド確定時の振る舞い（汎用性の検算）

**検算の対象は「ロードマップの骨組み（フェーズ計画・柱の分解）」であって「スキーマが一切
変わらないこと」ではない**（[01 §2](01-vision-and-principles.md) の2軸区別を参照）。総合モール型と
特化型は**ポリシー値の変更のみ**で吸収でき、B2B のみ一部で**柱の設計範囲内の構造拡張**を要する
——いずれの場合もフェーズ計画・柱の分解を組み直す必要はない、というのがここでの検算である:

| ブランド決定 | 吸収レベル | ロードマップ・骨組みへの影響 |
|---|---|---|
| 総合モール型 | ポリシーのみ | [03 §2](03-category-taxonomy.md) の20部門をそのまま有効化。ポリシー初期値のまま。骨組み変更なし |
| 特化型（例: ラグジュアリー） | ポリシーのみ | 部門の部分集合を有効化 + 属性必須化・返品期間延長・レビュー事前審査・販促頻度抑制など**ポリシー値の変更のみ**。骨組み不変 |
| B2B 寄り | ポリシー + 柱⑥内の構造拡張 | 審査を「全商品審査」モードに設定・措置閾値は緩和（ポリシー）。RMA に見積/交渉ステップを足す場合は ⑥ の**状態機械を拡張する構造変更**が入る（＝純粋なポリシー変更ではない）が、これは柱⑥の設計範囲内で吸収され、フェーズ計画・柱の分解の組み直しは不要 |

ブランド確定時は本表を実際の決定で上書きする（[README 更新規約](README.md#更新規約)）。
