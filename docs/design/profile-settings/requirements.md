# 顧客プロフィール設定機能 — 要件定義書 (requirements.md)

## 1. 機能要件 (Functional Requirements)

### F1: 会員情報の閲覧・編集
- **要件**: ログインユーザーは、自分の登録情報（氏名、メールアドレス、プロフィール画像等）を閲覧および編集できること。
- **受け入れ基準 (Acceptance Criteria)**:
  - Clerkの `<UserProfile />` コンポーネントを `/profile/settings` に適切に配置し、ユーザーが直感的に操作できる。
  - プロフィール画像の変更が正常に行われ、ヘッダー等の表示にも即座に反映されること。

### F2: セキュリティ設定の管理
- **要件**: パスワードの変更、多要素認証 (MFA) の設定ができること。
- **受け入れ基準**:
  - パスワード変更フローが安全に完了すること。
  - MFAの有効化手順が表示され、ワンタイムパスワードなどの認証が設定できること。

### F3: アカウントの削除 (退会手続き)
- **要件**: ユーザーは自身の意思でアカウントを完全に削除できること。
- **受け入れ基準**:
  - 退会ボタンを押した際、「本当に削除しますか？」という二段階の確認ダイアログが表示されること。
  - 削除実行時、Clerk上のユーザーアカウントが削除され、DB内の対応する `User` レコードも連動して削除または無効化（論理削除）されること。
  - セッションが破棄され、トップページ `/` へ安全にリダイレクトされること。

---

## 2. 非機能要件 (Non-Functional Requirements)

### N1: セキュリティと認可
- ログインしていないユーザーが `/profile/settings` に直接アクセスした場合は、Clerkのミドルウェアにより `/sign-in` へ強制リダイレクトされること。
- 他人のプロフィール設定情報を盗み見たり編集したりできないこと (IDORの完全防止)。

### N2: パフォーマンスと可用性
- Clerk UI コンポーネントの読み込み中にローディングスピナー等のプレースホルダーが表示され、画面がフリーズしないこと。

---

## 3. 制限事項・規約
- 会員情報の管理は基本的に Clerk 側にマスターデータを持たせるため、DBとの同期遅延が発生しないような実装とすること（Webhook もしくは更新 API 直後の状態確認）。
