## Why this matters

措置の仕組み（`StoreStatus.BANNED/DISABLED` + admin の店舗管理 UI）は在るのに、
**措置を判断する材料が構造的に存在しない**。注文の状態は enum で分かるが「いつ遷移したか」が
記録されず（`createdAt`/`updatedAt` のみ）、出荷遅延率が計算不能。`Store.averageRating` は
どのクエリも更新しない死にフィールド。キャンセル率・返品率の集約もない。
販売者数が増えるほど、運営は「なんとなく怪しい店舗」を勘で処分するか放置するかの二択になり、
カタログの信頼（Round 2 spike 016 が守る入口の品質）が継続運用で毀損されていく。
本 spike は Amazon の Account Health に相当する骨組み — **(a) 事実タイムスタンプ、
(b) 店舗メトリクス集約、(c) 閾値ポリシー → 措置の接続** — を、閾値・措置の厳しさを
ポリシー（データ）で差し替え可能な形で設計する。**分析ダッシュボードは作らない**
（`product.md` スコープ外 — 措置判断のシグナルと販売者への通知に限定）。

## Current state（設計前に必ず読む）

### 措置側 — 存在する（`prisma/schema.prisma:76-81` ほか）

```prisma
enum StoreStatus {              // schema.prisma:76
  PENDING
  ACTIVE
  BANNED
  DISABLED
}
```

- admin の店舗ステータス変更: `updateStoreStatus`（`src/queries/store.ts:531-602` —
  `$transaction` で status 更新 + PENDING→ACTIVE 時のロール昇格 + Clerk 同期）
- admin UI: `src/app/dashboard/admin/stores/`

### 判断材料側 — 存在しない

1. **事実タイムスタンプの欠落**（`prisma/schema.prisma:529-558,612-639`）:
   `OrderGroup` / `OrderItem` は `createdAt` / `updatedAt` のみ。
   `Shipped` になった時刻・`Delivered` になった時刻が残らないため、
   **「注文から出荷までの日数」「約束納期の遵守率」が計算不能**。
   `updatedAt` は任意の更新で動くため代用にならない。
2. **約束側は在る**（`schema.prisma:536-537`）:
   ```prisma
   shippingDeliveryMin Int   // OrderGroup — 注文時点の配送約束日数スナップショット
   shippingDeliveryMax Int
   ```
   「約束 vs 実績」の**実績側だけが無い**。
3. **評価シグナルは死んでいる**（`schema.prisma:93-94`）:
   `Store.averageRating` / `numReviews` は更新する query が無い（詳細: plan 019 / O-2）。
4. **率系メトリクスの集約なし**: キャンセル率（`OrderItem.status = Canceled` の比率）・
   返品率（同 `Returned`）・チケット率（`SupportTicket.orderId` → OrderGroup → storeId で
   店舗に帰属可能）を集約する仕組みが無い。

### 状態遷移の書き込み点（タイムスタンプ記録のフック候補）

- SELLER: `updateOrderGroupStatus`（`src/queries/order.ts:164`）/
  `updateOrderItemStatus`（`order.ts:229`）
- ADMIN: `updateOrderGroupStatusAsAdmin`（`order.ts:459`）/
  `updateOrderItemStatusAsAdmin`（`order.ts:521`）
- いずれも**任意ステータスへ自由遷移可能**（状態機械ガードなし — plan 018 O-1 でも指摘）。
  タイムスタンプ記録は「遷移の正しさ」に依存するため、この自由遷移が精度リスクになる

### 遵守すべきリポジトリ規約

- 認可は auth-guards。措置 action は `requireAdmin`
- 状態遷移 + タイムスタンプ記録 + 措置は `db.$transaction`
- スキーマ変更時は ERD 再生成（`.claude/rules/03-data-model-diagram-sync.md`）
- `src/` で `console.log` 禁止 / 構造化ログ2引数形式
- センシティブデータ（措置理由に含まれうる顧客情報）のログ出力禁止

## Open questions（spike が証拠付きで必ず答える）

1. **事実タイムスタンプの持ち方**: (a) 専用カラム（`shippedAt`/`deliveredAt` 等を
   OrderItem/OrderGroup に追加 — 単純・クエリ容易・遷移種別ごとにカラム増）、
   (b) イベントログテーブル（`OrderStatusEvent`: 対象・旧状態・新状態・実行者・時刻 —
   汎用・監査証跡になる・集計に JOIN 必要）のどちらか。**監査証跡（誰がいつ遷移させたか）の
   価値**と集計コストを比較して確定する。plan 018 の RMA 状態機械が同じ問いを持つため、
   018 と同一方式に揃えること（018 実行済みならその決定に従う）。
2. **メトリクスの定義**: 遅延率（**指標名と SLA 基準を一致させること** — `shippingDeliveryMax`
   は配送日数の上限なので、`deliveredAt` 基準で測るなら「配送遅延率」と呼ぶ。「出荷遅延」を
   測りたいなら別途「出荷 SLA」（`shippedAt` 基準の dispatch 期限）を定義する。出荷実績を
   配送 max と比較する現行定義は指標名と基準がねじれている。**さらに終端基準（`deliveredAt`）だけでなく
   計測の起点タイムスタンプも指標契約に固定すること** —— `shippingDeliveryMax`（許容日数）と
   比較する起点が注文作成時刻（`createdAt`）か出荷時刻（`shippedAt`）かで意味がまったく変わる。
   「配送遅延率」なら **起点=出荷時刻・終端=配達時刻・許容=`shippingDeliveryMax` 日**のように
   〈起点／終端タイムスタンプ・タイムゾーン・境界の丸め・いずれかが欠落した注文の除外規則〉を
   同じ指標契約に明記する。**未配達注文を一律に分母から除外しないこと** —— 除外規則は
   「終端が欠落しているか」ではなく「**SLA 期限を過ぎているか**」で分岐させる:
   - **期限超過かつ未配達** → 分子・分母の**両方に算入**（遅延として確定。未配達のまま
     期限を過ぎた注文こそ最悪ケースであり、これを除外すると遅延率が実態より良く出る
     生存者バイアスになる）
   - **期限内で未配達** → 打ち切り（censoring）として分母から除外（まだ遅延と判定できない）
   - **起点が無い**（未出荷 / backfill 前の履歴欠落）→ 分母から除外し、下の「計測開始日」で
     線引きする（遅延「あり」とも「なし」とも数えない）

   キャンセル率・返品率・評価（019 供給）・チケット率についても、同じ厳密さで
   各定義（分母・対象期間・最小注文数の足切り）を確定する。**新規店舗（サンプル数不足）の
   扱い**も決める。

   > **上の 3 分岐（期限超過かつ未達／期限内で未達／起点なし）を他指標へそのまま横展開しないこと。**
   > この分岐は `shippingDeliveryMax` という **SLA 期限が存在する**ことに依存している。
   > キャンセル率・返品率・評価・チケット率には対応する期限が無く、「期限超過かつ未達」という
   > 分岐自体が定義できない（何を以て「まだ判定できない」のかが別問題になる —— 例えば返品率なら
   > 「返品受付期間が終わっていない注文」が打ち切り対象だが、それは配送 SLA とは無関係の期間）。
   >
   > 横展開するのは**分岐の中身ではなく、分母定義を明文化する義務**である。各指標について
   > 次を個別に決めること:
   > - **分母に何を入れるか**（対象イベントの母集団）
   > - **まだ確定していない事象をどう扱うか**（打ち切りの有無と、その判定に使う時間軸。
   >   SLA 期限を持たない指標では「打ち切りなし」も正当な選択 —— ただし明示的に選ぶこと）
   > - **除外がバイアスを生まないことの確認**（配送で「未配達を一律除外すると遅延率が良く出る」
   >   のと同型の生存者バイアスが、その指標にも無いか）

   > **(必須) 全指標で共有する評価時点 `evaluationAt` を指標契約に含めること。**
   > 上の除外規則は「**SLA 期限を過ぎているか**」で分岐するが、その判定は現在時刻に依存する。
   > にもかかわらず、全注文に共通する評価基準時点が定義されていない。集計ジョブが
   > `now()` を行ごとに評価すると、**バッチ実行中に時刻が進むぶんだけ判定基準がずれる**:
   >
   > - 期限を「バッチ実行中に」跨いだ注文は、処理順によって
   >   「期限内で未配達（分母から除外）」にも「期限超過かつ未配達（分子・分母に算入）」にも倒れる
   > - 同じ期間を後から再集計しても**同じ数字にならない**（監査・異議申立てに耐えない）
   > - 店舗間の比較が、その店舗の行が処理された時刻という無関係な要因に汚染される
   >
   > 契約として次を定める:
   >
   > 1. 集計の開始時に `evaluationAt` を **1 回だけ**確定し、全行・全指標がその単一の値を使う
   >    （行ごとの `now()` 呼び出しを禁止する）
   > 2. `evaluationAt` を**集計結果と一緒に保存・出力する**。どの時点のスナップショットかを
   >    後から復元できないメトリクスは、措置判断（サスペンド等）の根拠に使えない
   > 3. 再集計・バックフィルでは過去の `evaluationAt` を**再利用できる**ようにする
   >    （「あの日の数字」を再現するため。現在時刻で上書きしない）
   >
   > 起点／終端タイムスタンプが「どの区間を測るか」を決めるのに対し、`evaluationAt` は
   > 「**いつの時点から見た区間か**」を決める別軸である。両方を指標契約に書くこと。

   > **(必須) 既存注文の履歴欠落と backfill 方針**: タイムスタンプ/イベントログを新設した時点で、
   > **既存の注文には `shippedAt`/`deliveredAt` が無い**（履歴欠落）。この扱いを設計項目にする:
   > - backfill しない場合、既存注文を遅延率等の**分母から除外**する（「実績データのある注文のみ」で
   >   率を計算）。導入直後に「データ無し＝優良/劣悪」と誤判定しないよう、
   >   「計測開始日」を持ち、それ以前の注文を集計対象外にする。
   > - `updatedAt` からの近似 backfill は**信頼できない**（任意更新で動くため）。近似する場合は
   >   「推定値」フラグを立て、措置判断には使わない等の縛りを明記する。
   > - 移行手順（補正マイグレーション新規作成・ERD 再生成）と「計測開始日」の初期値を決める。
   >
   > **(必須) 信頼できない状態遷移をメトリクスから除外する規則**: 現状は状態機械ガードが無く
   > 任意遷移が可能（Current state「状態遷移の書き込み点」参照）。不正・異常な遷移から記録された
   > タイムスタンプをそのまま集計すると指標が汚染される。除外規則を定義する:
   > - 遷移の妥当性は**状態列の合法性だけでなく、遷移させたアクターの認可**にも依存させる。
   >   合法な列（`Pending → Shipped → Delivered`）でも、その遷移を実行する権限が無いアクター
   >   （例: SELLER 自身による `Delivered` 偽装）は妥当ではない。列合法性のみで valid 判定すると
   >   下記 STOP 条件の偽装が素通りする — 記録時に「誰がこの遷移を行ったか」の認可を検査する。
   > - **(必須) 検査するだけでなく、遷移時点の認可結果を行に保存すること。**
   >   保存するのは最低限〈アクター id・**その時点のロール**・認可判定（valid/invalid とその理由）〉。
   >   ロールは後から変わりうる（SELLER が権限剥奪される / ADMIN に昇格する）ため、集計時に
   >   **現在のロールで再評価すると同じ期間の再集計が別の答えを返す**。これは `evaluationAt` の
   >   再現性契約（上の必須項目 2・3）と同じ要求であり、片方だけでは成立しない ——
   >   `evaluationAt` を固定しても、認可判定が「今のロール」で動けば数字は再現しない。
   >   集計は**保存済みの判定結果のみ**を読み、アクターのロールを引き直さないこと。
   >   （認可ロジック自体を後から修正した場合は、再評価ではなく**再判定バッチとして明示的に**
   >   走らせ、新しい `evaluationAt` の下で別スナップショットとして記録する。）
   > - **(必須) Webhook・システム起点の遷移について actor 契約を定義すること（2026-08-01 追加）。**
   >   上の必須項目は「アクター id・その時点のロール」を行に保存せよと定めているが、
   >   **状態遷移の一部には人間のアクターが存在しない**。本リポジトリの実在の書き込み点:
   >
   >   | 起点 | 遷移 | 人間の actor |
   >   |---|---|---|
   >   | Stripe / PayPal webhook（`src/app/api/webhooks/`） | `paymentStatus` → `Paid` 等 | **無し** |
   >   | 決済 capture の同期パス（`src/queries/stripe.ts` / `paypal.ts`） | 同上 | 購入者だが**販売者ではない** |
   >   | 将来のバッチ・再判定ジョブ（上の括弧書き） | 再スナップショット | **無し** |
   >
   >   契約を決めずに実装すると次のどちらかに倒れ、**どちらも壊れる**:
   >
   >   - actor id を **NOT NULL** にする → webhook 経由の遷移が**そもそも書けない**
   >     （回避のために購入者 id や店舗オーナー id を詰めると、**していない遷移を
   >     その人がしたことになる**。セラー品質指標なので、これは指標の汚染に直結する）
   >   - **nullable** にする → 「システム起点」と「actor を記録し忘れた」が
   >     **区別できない**。集計時にどちらを除外すべきか決められず、
   >     上の「不正な遷移を除外する」規則が機能しない
   >
   >   spike は最低限これを確定すること:
   >
   >   1. **actor は NOT NULL とし、システム主体にも必ず値を入れる**
   >      —— 「未記録」を表現できない状態にする。
   >
   >      > **ただし `User` への外部キーにはできない（2026-08-02 明示化）。** 予約 id
   >      > （例 `system:webhook:stripe`）に対応する `User` 行は存在しないため、
   >      > FK 制約が webhook / バッチ由来の遷移の**書き込み自体を拒否する**。
   >      > 「NOT NULL の actor id」とだけ書くと、素直に `actorId String @db.Uuid` +
   >      > `@relation(fields: [actorId], references: [id])` を引いてしまい、
   >      > **監査記録を保存できないスキーマ**が出来上がる。保存形式まで決めること。
   >      >
   >      > **第一候補: FK を張らない 2 列構成**
   >      >
   >      > ```prisma
   >      > actorType ActorType   // 下の 2. の独立列挙。NOT NULL
   >      > actorRef  String      // NOT NULL。人間なら Clerk user id、
   >      >                       // システムなら予約 id（system:webhook:stripe 等）
   >      > ```
   >      >
   >      > - **制約**: 両列 NOT NULL。`actorRef` の形式は `actorType` ごとに決まる
   >      >   （人間 = Clerk user id / システム = `system:<source>:<name>` の予約名前空間）。
   >      >   Clerk の id は `user_` 前缀なので `system:` と衝突しない。
   >      >   DB レベルで縛るなら、**列挙の全値を覆う双方向の CHECK** にすること:
   >      >
   >      >   ```sql
   >      >   CHECK (
   >      >       CASE actorType
   >      >           WHEN 'SYSTEM'  THEN actorRef LIKE 'system:%'
   >      >           WHEN 'WEBHOOK' THEN actorRef LIKE 'system:%'
   >      >           ELSE actorRef NOT LIKE 'system:%'   -- USER / SELLER / ADMIN
   >      >       END
   >      >   )
   >      >   ```
   >      >
   >      >   `actorType <> 'USER' OR …` の形にしないこと —— **人間ロールのうち
   >      >   `USER` しか縛らない**ため、`actorType='SELLER'` +
   >      >   `actorRef='system:webhook:stripe'` が通ってしまう。それは下の集計クエリ
   >      >   （`actorType = 'SELLER'`）が拾う行なので、**システム遷移が
   >      >   セラーの行動として指標に混入する** —— 本 spike が防ごうとしている
   >      >   まさにその取り違えが、制約をすり抜けて DB に入る。逆向き
   >      >   （`SYSTEM` に人間の id）も同時に塞ぐこと。
   >      > - **移行**: 既存行が無い新規テーブルなら単純追加。既存行に後付けするなら
   >      >   一旦 nullable で足し、backfill 後に `SET NOT NULL` する 2 段階
   >      >   （backfill の値が決められない行があるなら、それは 1 の前提が崩れている合図）。
   >      > - **集計クエリ**: 「セラーの行動を測る」指標は
   >      >   `WHERE actorType = 'SELLER'` に絞る。`ADMIN` を混ぜると
   >      >   運営の介入がセラーの実績として計上されるため含めない
   >      >   （`SYSTEM` / `WEBHOOK` を除くのと同じ理由）。
   >      >   `actorRef` を `User` と結合したいときは `LEFT JOIN` にする
   >      >   （システム行は結合先が無いので `INNER JOIN` だと黙って落ちる）。
   >      >
   >      > **代替: 予約システム行を `User` に持つ**。FK を維持できる代わりに、
   >      > 実在しない「ユーザー」が `User` テーブルに混ざり、ユーザー数の集計・
   >      > Clerk 同期・GDPR 削除フローすべてにこの例外を持ち込む。**採らないなら
   >      > その理由を spike の成果物に書き残すこと**（後続ラウンドの再検討を防ぐため）。
   >   2. **ロール列挙に人間ロール以外を持たせる** —— `Role`（`USER`/`SELLER`/`ADMIN`）を
   >      そのまま使わず、`SYSTEM` / `WEBHOOK` を含む**別の列挙**（上の `ActorType`）にする。
   >      Prisma の `Role` を拡張すると Clerk のロール同期と干渉するため分離すること
   >   3. **発生源を別列で持つ**（どの webhook / どのジョブか）。同じ `SYSTEM` でも
   >      Stripe webhook 由来と再判定バッチ由来は監査上の意味が違う
   >   4. **システム起点の遷移を valid とするか**を明示的に決める。決済確定は正当な
   >      遷移なので通常は valid だが、「セラーの行動を測る」指標に算入するかは別問題
   >      —— **算入しないなら valid かつ「指標対象外」フラグ**が要る
   >      （valid/invalid の 2 値では表現できない）
   >
   >   Q1(a)（専用カラム）/ Q1(b)（イベントログ）のどちらを採るかと**同時に**決めること。
   >   イベントログ方式なら上の 4 項目は行の属性になるが、専用カラム方式では
   >   遷移ごとに列が要るため、そもそも actor を保存できる形かが設計判断に影響する。
   > - 合法な遷移列（例: `Pending → Shipped → Delivered`）に沿って記録されたタイムスタンプのみを
   >   メトリクスに採用し、**逆行・スキップ・重複遷移由来の記録は除外/フラグ**する。
   > - イベントログ方式（Q1(b)）なら「旧状態→新状態」が合法かを記録時に判定し `valid` フラグを持つ。
   >   専用カラム方式（Q1(a)）なら記録時に遷移妥当性を検査してから書く。
   > - 「SELLER が Delivered を偽装して指標を操作」（下記 STOP 条件）への耐性もこの規則で扱う
   >   （偽装遷移を valid と誤認しない設計）。
3. **集計の実行方式**: リアルタイム（遷移時に増分更新）か日次バッチ（cron で再計算）か。
   Vercel 環境の制約（常駐不可）と、措置判断に必要な鮮度（日次で十分か）から確定する。
   集計結果の置き場（Store にカラム追加 vs 別テーブル `StoreHealthSnapshot`）も決める。
4. **閾値ポリシーのデータ化**: 「遅延率 > X% が N 日継続 → 警告、> Y% → DISABLED 候補」の
   ような規則をどう表現するか。ブランド確定時（例: B2B 寄りなら緩和）に**コード変更なしで**
   差し替え可能であること（OPERATIONS_TRUST_GROWTH_BLUEPRINT §1.2）。
5. **自動措置の human-in-the-loop**: 警告（販売者への通知 — plan 021 経由）は自動、
   `DISABLED`/`BANNED` は「候補としてキュー化し ADMIN が承認」とする初期仮説の妥当性を
   確認する。**完全自動の BAN は誤判定時の被害が大きい** — 自動化の段階（通知のみ →
   新規出品停止 → DISABLED）を設計する。
6. **販売者への可視化の最小形**: 販売者ダッシュボードに出すのは「健全性ステータス
   （良好/警告/危険）+ 警告理由 + 改善基準」まで、とする線引きが KPI（販売者の操作性）と
   スコープ外（高度分析）の両方に整合するかを確認する。

> - `updateStoreStatus`（`store.ts:531-602`）は **`requireAdmin` を前提**とし、**人間の ADMIN 主体**が
>   いることを想定する。自動評価パイプラインには admin ユーザー文脈が無いため、そのまま呼ぶと

> - また `updateStoreStatus` は **PENDING→ACTIVE 時のロール昇格 + Clerk 同期**を伴う。自動措置
>   （DISABLED 候補化等）でこの副作用を意図せず起こさない設計が要る。
> - **自動措置用の特権サービス境界を定義すること**: 「システム／サービスアクター」による措置実行を

>   切り出し、人間 admin 用 action とは別 API にする。何を自動で実行してよいか（通知・新規出品停止）と、
>   human-in-the-loop 必須の措置（DISABLED/BANNED は ADMIN 承認 — Q5）を境界で分ける。
> - **Clerk 同期を含む措置処理の失敗契約を明記すること**: 措置が Clerk 同期（外部呼び出し）を
>   含む場合の失敗時挙動を定義する — DB 状態更新と Clerk 同期の原子性（`$transaction` の内/外）、
>   Clerk 同期失敗時に DB 措置をロールバックするか／措置は確定させ同期をリトライキューに載せるか、
>   リトライ方針、部分失敗の可観測性（構造化ログ）。通知同様、外部同期の失敗が主状態を不整合に
>   しないモデルを 021 の tx 境界方針と揃える。

**Verify**: パイプライン図・閾値ポリシーのデータモデル・自動化段階の表に加え、

**Verify**: 後続プランの done criteria に「全遷移点の記録網羅性の検証手順」が含まれる。
**grep 単独を完了条件にしないこと** — 下記参照。

> **grep は網羅性を証明しない（棚卸しの入口であって、ゲートではない）。**
> grep は**テキスト**検索であり、「すべての遷移点がタイムスタンプを記録しているか」という
> **意味**の問いには原理的に答えられない。本リポジトリではこの乖離が実際に起きている:
>
> `src/queries/order.ts` のステータス書き込み 6 箇所は**すべて変数経由**であり、enum リテラルを
> 含まない:
>
> ```text
> :262  data: { status },              :579  data: { paymentStatus: status },
> :451  data: { status },              :587  data: { status: childOrderStatus },
> :500  data: { status },              :591  data: { status: childItemStatus },
> ```
>
> したがって `OrderStatus.Canceled` / `ProductStatus.Shipped` 等の enum 値で grep しても
> **実際の遷移点は 1 つもヒットしない**。呼び出し形も不揃いで（`update` 3・`updateMany` 3、
> 一部は `$transaction` 内にネスト）、構造パターンでの grep も安定しない。逆に無関係な箇所が
> ヒットする偽陽性も起きる。**「grep がクリーン = 網羅済み」は成り立たない。**
>
> 後続実装プランの done criteria は、以下の 3 層で網羅性を担保すること:
>
> 1. **列挙（grep はここで使う）**: 遷移点の候補一覧を grep + 型情報（`PaymentStatus` /
>    `OrderStatus` / `ProductStatus` を引数に取る、または `data` に書く関数）で機械的に作り、
>    **design doc に遷移点の確定表として固定する**。grep はこの棚卸しの入口として使い、
>    出力そのものを合格判定に使わない。
> 2. **各遷移点の挙動テスト**: 確定表の各行に対し、その遷移を実行してタイムスタンプ／イベント行が
>    実際に記録されることを検証するテストを 1 件以上置く。**記録の有無はテストで示す**
>    （テストが無い遷移点は「未検証」として表に明記する）。
> 3. **将来の追加に対する構造的ガード**: 新しい遷移点が追加されたときに記録漏れが起きない形を
>    設計する。推奨は**全遷移を単一のヘルパー経由に集約**し（`order.ts` の `restockOrderItems` /
>    `isRestockTerminalOrderStatus` が同型の先例）、直接 `update` する経路を規約で禁止すること。
>    集約すればヘルパー 1 箇所のテストが全遷移点をカバーし、網羅性の問いが構造で閉じる。
>    集約しない設計を採る場合は、**なぜ閉じるのか**を design doc で説明すること。

## STOP conditions

以下の場合は STOP して報告する:

- 事実タイムスタンプ or 状態遷移イベントログが既にスキーマに追加されている（前提消滅）
- Step 1 で、決済 webhook 経由の状態変更が seller action と異なる整合性モデル
  （例: webhook が `$transaction` 外で多段更新）を持ち、タイムスタンプの一貫記録が
  この spike の範囲で設計しきれないと判明した場合 — 前提整理のための独立調査を提案して報告する
- 閾値ポリシー機構が spike 016 の審査ポリシー機構と統合すべき（同一テーブルで表現可能）と
  判明した場合 — 統合案を添えて 016 との調整を仰ぐ（勝手に 016 の設計を変えない）
- **「SELLER が自店舗の注文を Delivered に偽装して指標を操作できる」問題を STOP 対象から除外しない**。
  これは既知だが**即時悪用可能な認可欠陥**であり、P1 として報告対象に含める（「既知だから報告不要」と
  切り捨てない）。この spike では:
  (i) 発見済みの事実として design doc / findings に明記し、
  (ii) 指標偽装への耐性を Open question 2 の「信頼できない遷移の除外規則」で設計論点として扱い、
  (iii) 併せて **SELLER が Delivered を勝手に立てられる遷移権限そのもの**（状態機械ガード欠如）を
       後続実装プランの必須修正項目として記録する。
- 上記**以外**の、即時悪用可能な認可欠陥を新たに発見した場合も — P1 発見としてただちに報告する。
