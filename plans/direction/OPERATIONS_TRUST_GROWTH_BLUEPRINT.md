## 1. 目的・前提

### 1.1 何を目指すか

Round 2 §1.1 の「Amazon 級 = 構造的性質」の定義を継承し、本ラウンドは残る2つの構造的性質を
土台化する:

5. **取引後の信頼ループ** — 買った後（返品・レビュー・問い合わせ）の体験が構造化されており、
   顧客と販売者の双方が「次も使う」理由になる（Amazon の返品体験・レビューエコシステムに相当）
6. **プラットフォームの自己調整力** — 販売者の品質が計測され、閾値ポリシーで自動的に
   措置・販促・露出が調整される（Account Health / セールイベント運営に相当）

### 1.2 設計原則（Round 2 §1.2 の継承）

ブランディング未定のため、**構造はブランド非依存・ポリシーはデータで差し替え**:

| 領域 | 構造（スキーマ・状態機械・seam） | ポリシー（データ/シードで差し替え） |
|---|---|---|
| 返品 RMA | RMA エンティティ + 状態機械 | 返品可能期間・可否条件・自動承認閾値 |
| レビュー | モデレーション状態 + 通報 + 集計 | 審査モード（事前/事後/無審査）・表示閾値 |
| 販促 | キャンペーン エンティティ + 価格履歴 | イベント種別・割引率上限・開催頻度 |
| 通知 | Notification テーブル + チャネル seam | イベント→通知マッピング・チャネル選択 |
| セラー品質 | 事実タイムスタンプ + メトリクス集約 | 措置閾値（警告/DISABLED/BANNED の基準） |

### 1.3 尊重する既決事項（再提案しないもの）

- `product.md` スコープ外: **多通貨・税計算エンジン・高度な分析ダッシュボード・配送キャリア連携**
  → 販促は単一通貨前提 / セラー指標は措置シグナルに限定（分析 UI は作らない）/
  RMA の返送追跡は追跡番号手入力前提
- Round 1 DIRECTION-01（返金実行）/ 02（restock = plan 012）/ 03（サポートコンソール）/
  04（i18n）/ 05（監視）は監査・配置済み。本ラウンドは**重複プランを作らず接続点のみ定義**する
- Round 2 spike 013〜017（カタログ・検索・審査・レコメンド）とは in-scope が重ならない
  （唯一の接続: spike 016 の審査通知が通知基盤 ⑨ を消費する）

## 2. 現状分析 — 資産と欠落

詳細エビデンスは findings-10 参照。要約:

### 2.1 資産（再利用できる既存構造）

| 資産 | 根拠 | 本ラウンドでの意味 |
|---|---|---|
| `SupportTicket` + `RETURN_REQUEST` カテゴリ + 受付フォーム | `schema.prisma:755-781` / `returns-exchange/page.tsx` | RMA の受付面は在る。構造化（対象アイテム・状態機械）だけが欠落 |
| `ProductStatus` に `Returned`/`Refunded`/`ExchangeRequested` 定義済み | `schema.prisma:560-610` | RMA の解決が接続すべき状態は既に enum に在る |
| PLATFORM スコープのクーポン + admin CRUD/UI + CAS 適用 | `coupon.ts:349-486` / `dashboard/admin/coupons/` | 販促エンジンの土台。キャンペーン層を上に足すだけ |
| `Message.isRead`/`readAt` の既読管理パターン | `schema.prisma:743-744` | アプリ内通知の未読管理の実装先例 |
| `OrderGroup.shippingDeliveryMin/Max`（配送約束のスナップショット） | `schema.prisma:536-537` | 遅延率計測の「約束」側は在る。「実績」側だけがない |
| 店舗承認 `$transaction` パターン（PENDING→ACTIVE + ロール昇格） | `updateStoreStatus`（`store.ts:612-644`） | **DB 状態遷移の原子化**テンプレート（RMA/措置に転用）。tx 内は DB の状態遷移のみ、**通知・外部同期は tx の外** — 境界は下記注記 |

> **店舗承認パターンの tx 境界（RMA・措置・審査に転用する際の必須の読み取り）**:
> `updateStoreStatus` が原子化しているのは **DB の状態遷移だけ**である
> （`store.ts:612-635` の `db.$transaction` 内は `store.update` +
> ロール昇格の `user.update` の 2 つのみ）。**Clerk メタデータ同期は tx の外**に置かれ、
> 「冪等操作でリトライ可能」というコメントつきで tx 成功後に実行される
> （`store.ts:637-644`）。
>
> **外部呼び出しを tx 内に入れてはならない**理由:
> 1. 外部 API の遅延がそのまま DB のトランザクション時間・ロック保持時間になる。
> 2. 外部呼び出しが成功した後に tx がロールバックすると、**DB は巻き戻るが外部システムは
>    巻き戻らない**（復元不能な不整合）。
>
> したがって柱⑥（RMA）・⑩（措置）に転用する際も、**tx 内 = DB の状態遷移、
> tx 外 = 通知送信・決済プロバイダ呼び出し・Clerk 同期**という分割を守ること。
> tx 外の副作用は**冪等に設計してリトライで担保する**（上記 Clerk 同期と同じ考え方）。
> 柱⑨（通知基盤）の Outbox 方式の検討は、まさにこの「tx 外の副作用をどう確実に届けるか」
> という問題への回答候補である。

### 2.2 欠落（拡張を阻む構造的制約 — Round 2 の B-1〜B-5 に続く採番）

| # | 制約 | 根拠 | 影響 |
|---|---|---|---|
| B-6 | **返品が自由記述チケット止まり**（RMA エンティティ・状態機械なし） | O-1 | 返品体験が運営の手作業に比例。DIRECTION-01（返金）が接続する上流が存在しない |
| B-7 | **レビューの信頼装置がない**（購入検証・モデレーション・通報・集計の原子性） | O-2 | UGC が増えるほど信頼が毀損するリスク。`Store.averageRating` は死にフィールド |
| B-8 | **販促がクーポンのみ**（キャンペーン構造・価格履歴・利用制限なし） | O-3 | プラットフォーム主導のセールイベントが企画できない。二重価格の根拠データもない |
| B-9 | **通知基盤ゼロ**（Notification モデルなし・メール送信手段なし・pull 型のみ） | O-4 | 016 審査・B-6 RMA・DIRECTION-03 がそれぞれ個別実装に向かい発火点が散乱する |
| B-10 | **セラー品質シグナルの不在**（事実タイムスタンプなし・メトリクス未集約） | O-5 | BANNED/DISABLED という措置だけあり判断根拠がない。品質の自己調整が働かない |

**依存の骨格**: B-9（通知）は B-6（RMA）と spike 016（審査）の共通前提。
B-7 と B-10 は評価集計の欠陥を共有（レビュー集計の修正がセラー指標の1系統を供給）。
B-8 は独立。

## 3. 汎用骨組みのアーキテクチャ方針 — 5本柱（⑥〜⑩）

Round 2 の柱①〜⑤に続く採番。**⑨（通知）が他の柱の共通前提**であり、
⑥⑦⑩は「信頼ループ」、⑧は「成長」を担う。各柱が spike プラン 1 本に対応する。

### ⑥ 返品・交換 RMA ワークフロー → [spike 018](../018-spike-returns-rma-workflow.md)

- `ReturnRequest`（仮称）エンティティを導入: 対象 `OrderItem`・数量・理由コード・
  解決種別（返金/交換/店舗クレジット）・状態機械（申請→承認/却下→返送待ち→受領検品→解決）
- 既存資産と接続する: 受付は `SupportTicket(RETURN_REQUEST)` からの昇格 or 注文履歴からの
  直接申請 / **解決時に `OrderItem.status` をどの終端値へ遷移させるかは未確定**
  （`Returned` が第一候補だが、解決種別ごとに答えが異なる — 下記 `TODO(needs-detail)` で
  確定させるまで決め打ちしない）/ 下流に DIRECTION-01（返金実行）と plan 012（restock）が接続
- **下流に接続する通知**: RMA の各状態遷移（申請受理 / 承認・却下 / 返送待ち / 受領検品 /
  解決）は**柱⑨（通知基盤）の発火点**になる。本柱⑥の状態機械が発火点の一覧を確定させ、
  柱⑨がイベント→通知マッピングとして受ける（⑨側の記述と対で維持すること）。
- 決めるべきこと: SupportTicket と RMA の関係（昇格 or 並立）/ 状態機械の遷移ガード実装
  （現状 `updateOrderItemStatus` は任意遷移可能 — O-1）/ 返品ポリシーのデータ化
- > **TODO(needs-detail)**: **解決種別ごとの終端状態の設計が未確定**（設計判断のため
  > ユーザー確認が必要）。解決種別は「返金 / 交換 / 店舗クレジット」の 3 つだが、
  > **それぞれ終端の意味が異なる**:
  > - **返金**: `OrderItem.status` は `Refunded` か `Returned` か（両方必要か）。
  >   DIRECTION-01（実返金実行）の完了と `PaymentStatus.Refunded` との関係は。
  >   部分返金時の終端は。
  > - **交換**: 元の `OrderItem` の終端は何か（`Returned`?）。**代替品の発送は
  >   新規注文として起票するのか、同一注文内で扱うのか**（在庫・売上計上・
  >   配送料の扱いが分岐する）。
  > - **店舗クレジット**: **クレジット残高を保持するエンティティが現状存在しない**
  >   （新規モデルが必要）。終端は `Returned` + クレジット付与の記録か。
  >
  > **これらは plan 012（restock）の発火条件とも直結する**
  > （[`audit/findings-08-direction.md`](../audit/findings-08-direction.md) の
  > DIRECTION-02 で status ごとに発火条件を分離した議論を参照 — 特に
  > 「Refunded は金銭の状態であって商品の所在を意味しない」点）。
  > **終端状態が決まらないと spike 018 の状態機械が閉じない**ため、
  > 設計着手前にユーザーと確定させること。
  （期間・対象外カテゴリ。`Store.returnPolicy String` の構造化を含む）

### ⑦ レビュー・UGC 品質ガバナンス → [spike 019](../019-spike-review-ugc-governance.md)

- レビューに (a) 購入検証バッジ（OrderItem 履歴との照合）、(b) モデレーション状態機械
  （公開/審査中/非公開/通報済み）+ 通報受付、(c) `$transaction` によるアトミック評価集計
  （Product と **死にフィールド化している Store.averageRating** の両方）、(d) helpful 投票の
  per-user 化（`likes Int` の置き換え）を導入
- モデレーションモード（事前/事後/無審査）は spike 016 と同じ「ポリシーをデータで差し替え」
- 決めるべきこと: 購入検証の判定基準（Delivered のみか）/ 通報の受け皿
  （SupportTicket 拡張 vs 専用モデル）/ `rating Float` の Decimal 化の要否

### ⑧ プロモーション・キャンペーンエンジン → [spike 020](../020-spike-promotion-engine.md)

- 3層で拡張する: (a) `Coupon` の表現力（型付き日付・固定額/率・利用回数上限・最低購入額・
  対象絞り込み）、(b) プラットフォーム主導キャンペーン エンティティ（期間・対象商品・
  割引・編成 — 現状の販売者自己申告 `isSale` の上位構造）、(c) 価格履歴テーブル
  （二重価格表示の根拠・`saleEndDate String` の型付け直しを含む）
- 既存の PLATFORM クーポン基盤・CAS 適用・admin UI は再利用する
- 決めるべきこと: キャンペーンと variant セールの優先順位・併用規則 / 価格履歴の粒度
  （サイズ単位か variant 単位か）/ セール自動終了の実行方式（cron vs 読み取り時判定）

### ⑨ 通知・トランザクショナルメッセージ基盤 → [spike 021](../021-spike-notification-foundation.md)

- 3点セット: (a) `Notification` テーブル（アプリ内通知の SSOT・`Message.isRead` パターン踏襲）、
  (b) 送信チャネル抽象（in-app 必須 + email はプロバイダ差し替え可能な seam —
  レコメンドの `getRelatedProducts(strategy)` seam と同じ発想）、(c) イベント→通知マッピングの
  データ化（どのイベントでどのロールに何を送るか）
- **最初の消費者は spike 016（審査合否）と spike 018（RMA 状態遷移）**。注文状態遷移
  （`updateOrderGroupStatus` 等）への後付けも設計に含める
- **接続点（柱⑥ RMA との双方向整合）**: **RMA の状態遷移で通知を発火する**
  （申請受理 → 承認/却下 → 返送待ち → 受領検品 → 解決 の各遷移で、
  顧客とセラーのどちらに何を送るかをイベント→通知マッピングに定義する）。
  柱⑥側（[spike 018](../018-spike-returns-rma-workflow.md)）の状態機械が
  **発火点の一覧を確定**させ、本柱⑨がその**配送手段**を提供する、という分担。
  > 柱⑥の記述と本柱⑨の記述は**対で維持**すること。片方だけに書くと、
  > 「RMA が通知を出す」ことが設計から落ちるか（⑥にしか書かないと⑨のマッピングに
  > RMA イベントが載らない）、通知の発火点が不明なまま実装される（⑨にしか
  > 書かないと⑥の状態機械に発火点が定義されない）。
- 決めるべきこと: email プロバイダ選定（ADR 化）/ 送信の実行モデル
  （同期送信 vs Outbox テーブル + 遅延処理 — Vercel 環境の制約込み）/ 通知設定（ユーザーの opt-out）

### ⑩ セラーパフォーマンス指標と自動措置 → [spike 022](../022-spike-seller-performance-trust.md)

- 3層: (a) **事実タイムスタンプ**（OrderItem/OrderGroup の状態遷移記録 — `shippedAt`/`deliveredAt`
  相当。イベントログ型 vs カラム型は spike で判断）、(b) 店舗メトリクス集約（遅延率 =
  約束 `shippingDeliveryMin/Max` vs 実績 / キャンセル率 / 返品率 / 評価 — ⑦の集計修正が供給）、
  (c) 閾値ポリシー（データ化）→ 措置（警告 → DISABLED → BANNED）の接続
- 分析ダッシュボードは作らない（スコープ外）。措置判断と販売者への通知（⑨経由）に限定
- 決めるべきこと: タイムスタンプの持ち方（イベントログ vs 専用カラム）/ 集計の実行方式
  （リアルタイム vs 日次バッチ）/ 自動措置の human-in-the-loop 要件（BANNED は人間承認必須か）

### ブランド確定時の振る舞い（汎用性の検算 — Round 2 §5 の表を拡張）

| ブランド決定 | 本ラウンドの骨組みへの影響 |
|---|---|
| 総合モール型 | ポリシー初期値のまま。変更なし |
| 特化型（例: ラグジュアリー） | 返品期間延長・レビュー事前審査・販促頻度抑制など**ポリシー値の変更のみ**。構造は不変 |
| B2B 寄り | RMA に見積/交渉ステップを追加する可能性のみ ⑥ の状態機械拡張で吸収。措置閾値は緩和 |

## 5. 既存プラン・規約との整合

- **in-scope の競合なし**: spike 018〜022 はいずれも読み取り調査 + 設計文書のみで、
  Round 1（001〜012）・Round 2（013〜017）のどのプランとも編集対象が重ならない
- **接続点の明示**: 021⇢016（審査通知）/ 018⇢DIRECTION-01・012（返金・restock）/
  019⇢022（評価集計）/ 022⇢016（BANNED 店舗の露出チェック）— 各 spike の Executor 指示に
  接続仕様の確認手順を記載する
- **規約遵守**（実装フェーズで適用）: 金額系は `Decimal(12,2)` + `Prisma.Decimal` 演算
  （⑧の価格履歴・固定額クーポンで必須）/ 状態遷移 + 副作用は `db.$transaction`
  （⑥⑦⑩で必須）/ auth-guards 使用 / `src/queries/` 配置 / スキーマ変更時は
  `03-data-model-diagram-sync`（ERD 再生成）と `safe-migration` スキル /
  コミットは `02-tdd-step-commit` の粒度規律
- **`rating Float` / `Size.discount Float` の扱い**: tech.md の Float 禁止規約は金額フィールド
  対象だが、⑦⑧の spike では評価・割引率の型見直し（Decimal 化 or 現状維持の明示判断）を
  ADR 判断項目に含める
