## 1. 目的・前提

### 1.1 何を目指すか

本プロジェクトを「Amazon 級の世界トップクラス EC サイト」へ拡張するための**構造上の土台**を
定義する。ここで「Amazon 級」とは GMV や品揃えの規模ではなく、**構造的性質**を指す:

1. **カテゴリ横断性** — 家電もファッションも食品も、同一のカタログ基盤で破綻なく扱える
2. **発見性** — 数十万 SKU でも顧客が「探せる・絞れる・出会える」（検索 / ファセット / レコメンド）
3. **セルフサービスな販売者体験** — 出店から出品までがガバナンス（審査）付きで自走する
4. **運営コストの逓減** — カタログが増えても ADMIN の手作業が線形に増えない

### 1.2 ブランディング未定 → 「構造優先」の設計方針

ブランドの方向性（総合モール型か、特化型か、ラグジュアリー寄りか）は**未定**である。
したがって本ブループリントは次の原則で書く:

- **構造（スキーマ・クエリ・ワークフロー）はブランド非依存に設計する。**
  カテゴリツリーの深さ・属性の種類・審査の厳しさは、すべて**データとして差し替え可能**にする
- **コンテンツ（タクソノミーの中身・属性定義・審査ポリシー）はシードデータとして提供する。**
  §3 の参照タクソノミーは「初期値」であり、ブランド確定時に絞り込み・入れ替えを行う前提
- 特化型ブランドに転じる場合は参照タクソノミーの**部分集合を有効化**するだけで済む構造にする
  （例: ラグジュアリー特化なら「ファッション/ジュエリー&時計/ビューティー」のみ有効化）

### 1.3 尊重する既決事項（本ブループリントが再提案しないもの）

- `product.md` スコープ外: **多通貨・税計算エンジン・高度な分析ダッシュボード・配送キャリア連携**
  → §5 の「ゲート付き将来項目」に位置のみ記す
- Elasticsearch 再導入はしない（tsvector 選定は決定済みトレードオフ）。検索拡張は tsvector の
  延長線で設計する（spike 015）
- SaaS 化 Phase 2/3（orgId/RLS・課金）は `saas-roadmap.md` 自身が「現時点では不要」とゲート済み
- Round 1 の direction 発見（DIRECTION-01 返金実行 / 02 restock / 03 サポートコンソール /
  04 i18n / 05 監視）は監査済み。本ブループリントは§5 でロードマップ上に**配置**するのみ

## 2. 現状分析 — 何が強みで、何がボトルネックか

詳細エビデンスは findings-09 参照。要約:

### 2.1 強み（Amazon 型カタログと既に整合している部分）

| 資産 | 根拠 | 拡張時の意味 |
|---|---|---|
| **バリアントレベルの価格・在庫・画像**（Product → ProductVariant → Size） | `schema.prisma:130-216` | Amazon の「親 ASIN / 子 ASIN」構造と同型。カタログの核は作り直し不要 |
| **店舗承認ワークフロー**（PENDING→ACTIVE + ロール昇格の `$transaction`、**Clerk 同期は tx 外**） | `store.ts:531-602` | 商品審査（spike 016）の設計テンプレートになる。**下記の境界に注意** |
| **金額 Decimal(12,2) 規律・配送料 SSOT・auth-guards** | `.claude/steering/tech.md` | 拡張しても品質規約が既に効く |
| **レコメンドシグナルの収集**（views / sales / rating / Wishlist / 注文履歴） | findings-09 E-5 | データは貯まっている。活用層（spike 017）を足すだけ |
| **`relatedProducts: []` の予約スロット** | `product.ts:1080` | 商品ページの UI 契約が既にレコメンドを想定 |

> **店舗承認ワークフローの原子性境界（spike 016 が模倣する前に正確に把握すること）**:
> `updateStoreStatus`（`store.ts:531-602`）の `$transaction` が包むのは
> **DB 更新の 2 つ（`store.update` の status + `user.update` のロール昇格）だけ**であり、
> **Clerk の `updateUserMetadata` は `$transaction` の外**で実行される外部 API 呼び出し
> （`store.ts:584` 付近。tx 成功後に `updatedStore.status === "ACTIVE"` を条件に発火）。
> - **なぜ tx 外か**: 外部 API は DB トランザクションに参加できない
>   （ロールバックできない・tx 内で待つと DB 接続を外部レイテンシの間占有する）。
>   これは欠陥ではなく妥当な設計。
> - **したがって「DB とクレデンシャル基盤が原子的に同期する」わけではない**:
>   tx コミット後に Clerk 呼び出しが失敗すると、**DB は SELLER・Clerk メタデータは
>   旧ロール**という不整合が残りうる（冪等操作なのでリトライ可能、というのが現設計の前提）。
> - **spike 016（商品審査）がこのテンプレートを流用する場合**、外部同期の失敗時の
>   契約（リトライ / outbox / 補償）を設計項目として明示すること。
>   関連: plan 035 がこの非対称（DB 昇格は PENDING 起点限定・Clerk 同期は結果が ACTIVE なら毎回）を
>   統合テストで固定する。

### 2.2 ボトルネック（拡張を阻む構造的制約）

| # | 制約 | 根拠 | 影響 |
|---|---|---|---|
| B-1 | **カテゴリが固定2階層**（Category→SubCategory、self-relation なし） | E-1 | 「家電 > カメラ > レンズ > 単焦点」が表現不能。総合モールの部門構造が組めない |
| B-2 | **商品属性が自由記述 Spec**（型なし・カテゴリ非依存・検索非参照） | E-2 | ファセット検索・商品比較・構造化データが成立しない。表記揺れが蓄積 |
| B-3 | **検索が2系統併存で貧弱**（tsvector は name+description のみ / ブラウズは ILIKE、ファセット集計なし、価格ソートなし） | E-3 | SKU 増加とともに「探せない」が顕在化。tsvector 経路は GIN 式インデックス `Product_fulltext_idx` で裏打ち済みだが対象が name+description に限られ、`index-products` 経路の Prisma per-column `{ search }` と ILIKE フォールバックはインデックス不使用（[findings-03](../audit/findings-03-performance.md)） |
| B-4 | **商品レベルの審査・公開制御がない**（保存即公開。BANNED 店舗の商品露出も未検証） | E-4 | 販売者数が増えるとカタログ品質と信頼性が守れない |
| B-5 | **シグナル未活用**（relatedProducts 常に空） | E-5 | 回遊・クロスセルの機会損失。単品ページが行き止まり |

B-1 → B-2 → B-3 は**依存の鎖**になっている（属性はカテゴリに紐づき、ファセットは属性に紐づく）。
これが §5 のフェーズ順序を規定する。

## 3. 参照カテゴリタクソノミー（ブランド非依存・シードデータ差し替え可能）

### 3.1 設計原則

1. **トップレベルは「部門（Department）」= 顧客のメンタルモデルの入口**。Amazon・楽天・
   Walmart のグローバル EC で共通して現れる部門を採用し、特定ブランドに寄せない
2. **深さは可変（実運用 3〜4 階層、上限は設けない）**。リーフノードにのみ商品を紐づける運用を
   推奨するが、スキーマとしては中間ノードへの紐づけも許す（移行期の互換のため — spike 013）
3. **タクソノミーはコードでなくシード**: `prisma/seed/` に参照タクソノミーを投入するシーダーを
   置き、ブランド確定時は有効化フラグ（またはシードの差し替え）で絞り込む
4. **属性セット（§4-②）はカテゴリに紐づく**: 部門ごとに「この部門の商品はこの属性を持つ」を
   定義するのがファセット検索の前提

### 3.2 参照トップレベル部門（20部門）

ブランド未定の初期値として、グローバル総合 EC で標準的な 20 部門を提案する。
各部門に 2〜3 階層目の例示と、支配的なバリアント軸・代表ファセットを付す
（現行スキーマのバリアント軸は Size/Color 固定 — E-2 — のため、「軸」列は spike 014 の要件になる）:

| # | 部門 | 2〜3階層目の例 | 支配的バリアント軸 | 代表ファセット属性 |
|---|---|---|---|---|
| 1 | 家電・カメラ | テレビ > 有機EL / カメラ > レンズ > 単焦点 | 容量・型番 | 画面サイズ, 解像度, 接続規格 |
| 2 | パソコン・周辺機器 | ノートPC / キーボード > メカニカル | 構成(RAM/SSD) | CPU, メモリ, OS |
| 3 | スマートフォン・アクセサリ | 本体 / ケース > 手帳型 | 容量・色 | 対応機種, 通信規格 |
| 4 | ファッション（婦人・紳士・子供） | 婦人 > ワンピース / 紳士 > シャツ | **サイズ・色**（現行軸そのまま） | 素材, 丈, 柄, シーズン |
| 5 | シューズ・バッグ | スニーカー / トート | サイズ・色 | 素材, ヒール高, 防水 |

| 10 | ホーム・キッチン | 調理器具 > フライパン / 寝具 | サイズ・色 | 素材, 対応熱源, 食洗機可 |
| 11 | 家具・インテリア | ソファ / 照明 | サイズ・張地 | 幅×奥行×高さ, 組立要否 |
| 12 | DIY・工具・ガーデン | 電動工具 / 園芸用品 | 電圧・サイズ | 電源方式, 対応径 |
| 13 | スポーツ・アウトドア | キャンプ > テント / 自転車 | サイズ・色 | 収容人数, 耐水圧, 重量 |
| 14 | おもちゃ・ホビー | ボードゲーム / プラモデル | — (単一SKU多め) | 対象年齢, プレイ人数, スケール |
| 15 | 本・雑誌・メディア | 書籍 > 技術書 / 音楽 | 判型・フォーマット | 著者, 出版社, 発売日, 言語 |
| 16 | ゲーム | 本体 / ソフト | エディション | 対応機種, CERO, ジャンル |
| 17 | ベビー・マタニティ | ベビーカー / おむつ | サイズ・個数 | 対象月齢, 安全基準 |
| 18 | ペット用品 | ドッグフード / トイレ用品 | 内容量・サイズ | 対象動物, ライフステージ |
| 19 | 自動車・バイク用品 | タイヤ / カー用品 | サイズ(規格) | 適合車種, 規格(例:205/55R16) |
| 20 | 文具・オフィス | 筆記具 / 収納 | 色・個数 | 規格(A4等), インク色 |

**読み方**:
- 4〜6（ファッション系）は現行の Size/Color 軸がそのまま効く = **現状の実装が最も得意な領域**。
  逆に 1〜3・15・19 は「容量」「判型」「規格」という第3の軸/属性が必須で、B-2 の解消
  （spike 014）なしには正しく扱えない
- 8・9・17 は法規・安全基準の表示義務が絡むため、**属性の必須化**（カテゴリ別必須属性 —
  spike 014 の中心機能）が単なる UX でなくコンプライアンス要件になる
- ブランド特化に転じる例: ラグジュアリー寄せ → 4/5/6/7 のみ有効化 + 属性「素材/原産国」を
  必須化。テック寄せ → 1/2/3/16 のみ有効化

### 3.3 タクソノミー運用ルール（シード設計の要件）

- ノードには `slug`（URL 安定・既存 `Category.url @unique` を継承）、表示順 `sortOrder`
  （現状 `updatedAt desc` 順 — E-1 — の置き換え）、`featured`（既存踏襲）、有効化フラグを持たせる
- **リーフ以外への商品紐づけは新規では禁止**（移行期の既存データのみ許容 → spike 013 の移行戦略）
- カテゴリ削除はハード delete（`category.ts:181-203`）から「無効化 + 商品の付け替え先指定」へ
  改める（Amazon の browse node 廃止運用と同じ発想）

## 4. 汎用骨組みのアーキテクチャ方針 — 5本柱

各柱が spike プラン 1 本に対応する。**柱①②が土台、③④⑤はその上に立つ**。

### ① カテゴリ N 階層ツリー（browse node 化） → [spike 013](../013-spike-category-tree-n-level.md)

- `Category` に self-relation（`parentId` + `depth` + materialized path）を導入し、
  `SubCategory` を統合する方向を第一候補として検討
- 影響範囲が本ブループリント中最大: `Product.categoryId/subCategoryId` の二重 FK、
  Zod スキーマ、商品フォーム、URL 構造（`filters.category`/`subCategory`）、admin UI、
  シーダー、E2E — spike 013 はこの**移行戦略（新旧並走 or 一括移行）の確定**が主目的
- 決めるべきこと: ツリー表現（隣接リスト + path か closure table か）/ 旧 `SubCategory` の
  データ移行 / URL 後方互換（既存 slug を生かすか）

### ② カテゴリ別属性スキーマ（ファセット基盤） → [spike 014](../014-spike-category-attributes-facets.md)

- カテゴリノードに「属性定義」（名前・型・単位・許容値・必須/任意・ファセット対象か）を紐づけ、
  商品/バリアントが「属性値」を持つ 2 層構造
- 既存 `Spec`（自由記述）は**残しつつ「その他仕様」へ降格**し、構造化属性を主役にする移行案を検討
- 決めるべきこと: 属性値の格納（正規化テーブル vs JSONB + GIN）/ 商品フォームの動的生成
  （React Hook Form + Zod の動的スキーマ）/ §3.2 の代表ファセットをシードにする範囲

### ③ ファセット検索・ブラウズ → [spike 015](../015-spike-faceted-search-and-browse.md)

- tsvector を**生成列 + GIN インデックス**に載せ替え、対象を name/description から
  brand・variant keywords・カテゴリ名へ拡大
- ブラウズ（`getProducts`）と検索（`search-products` route）の**2系統を統合**し、
  属性ファセットの件数集計・価格ソートを追加
- 決めるべきこと: ファセット集計の実行方式（GROUP BY vs マテビュー vs キャッシュ）/
  PERF-05（参照データキャッシュ）との統合 / `filters: any`（`product.ts:602`）の型付け

### ④ カタログガバナンス（出品審査） → [spike 016](../016-spike-seller-onboarding-catalog-approval.md)

- 既存の店舗承認（StoreStatus）の商品版: `Product` に公開状態（DRAFT / PENDING_REVIEW /
  ACTIVE / REJECTED / SUSPENDED 相当）を導入
- **審査モードをポリシーとして選べる**構造にする（全商品審査 / 新規販売者のみ / 事後審査）—
  ブランド未定のため、厳格さをデータで切り替えられることが「汎用骨組み」の要件
- 併せて BANNED/DISABLED 店舗の商品がストアフロントに露出していないかを検証し、
  漏れていれば公開クエリの共通 where に店舗状態を組み込む
- 決めるべきこと: ProductStatus という enum 名が**注文アイテム配送状態に既に使われている**
  （`schema.prisma:560`）ため命名の衝突回避 / 審査 UI は admin/orders の TanStack table
  パターン再利用

### ⑤ レコメンド基盤（ルールベース v1） → [spike 017](../017-spike-recommendation-foundation.md)

- 外部 ML 基盤なしで、既存シグナルの SQL 合成による v1:
  「同一リーフカテゴリ × views/sales 上位」（関連商品）、「共起注文」（一緒に購入）、
  「wishlist 人気」— `relatedProducts: []`（`product.ts:1080`）のスロットを埋める
- **インターフェイスを固定**（`getRelatedProducts(productId, strategy)` のような seam）し、
  将来の協調フィルタリング/ベクタ検索への差し替え点を作ることが真の目的
- スコープ外の「高度な分析ダッシュボード」とは線を引く: レコメンドは購買動線の機能であり
  分析 UI は作らない

## 5. フェーズ別ロードマップ

既存プラン（Round 1: 001〜012）と DIRECTION-01〜05 を含めた全体地図。
**Phase 0 が最優先である点は Round 1 の勧告から不変**。

> **Round 3 追記（2026-07-10）**: `[R3]` 表記の spike 018〜022（B-6〜B-10 の解消）を
> Phase C/D に配置した。B-6〜B-10 の定義と配置根拠は
> [`OPERATIONS_TRUST_GROWTH_BLUEPRINT.md`](OPERATIONS_TRUST_GROWTH_BLUEPRINT.md) §2.2/§4 を参照。

```
Phase 0: 守り（既存 Round 1 プラン — 拡張の前提）
├─ 001-004 セキュリティ（IDOR / mass-assignment / 決済信頼 / Clerk升级）★最優先
├─ 005-006 正確性（カート原子性 / 二重注文）
└─ 007-011 技術負債・テスト・docs

Phase A: カタログ基盤（土台 — 本ラウンドの中核）
├─ spike 013 → カテゴリ N 階層ツリー化       [B-1 解消]
└─ spike 014 → カテゴリ別属性スキーマ         [B-2 解消, 013 に依存]

Phase B: 発見性
├─ spike 015 → ファセット検索・ブラウズ統合    [B-3 解消, 014 に依存]
└─ (deferred PERF-05: 参照データキャッシュを 015 に統合検討)

Phase C: 信頼性・運用（マーケットプレイスの「治安」）
```

### 順序の根拠

- **Phase 0 → A**: セキュリティ・正確性の穴の上に構造改修を積まない（Round 1 勧告の維持）
- **A → B**: ファセット検索（③）は属性（②）が、属性はカテゴリツリー（①）が前提という
  依存の鎖（§2.2）。逆順で作ると手戻りが確定する
- **C は A と並行可能**: 出品審査（④）はカテゴリ構造に依存しないため、Phase A と並走できる。
  チケット→返金→restock は findings-08 の分析どおり「チケットが起点」の順で接続
- **D は最後**: レコメンドの効果はカタログの構造化（A）と回遊導線（B）の質に比例する。
  ただし spike 017 の「共起注文 SQL」だけは独立に PoC 可能

### ブランド確定時の振る舞い（本ロードマップの汎用性の検算）

| ブランド決定 | ロードマップへの影響 |
|---|---|
| 総合モール型 | §3.2 の 20 部門をそのまま有効化。変更なし |
| 特化型（例: ラグジュアリー） | 部門の部分集合を有効化 + 属性必須化ポリシー変更。**フェーズ構造は不変** |
| B2B 寄り | Phase C の審査を「全商品審査」モードに設定。**構造は不変** |

いずれのケースでも骨組み（スキーマ・クエリ・ワークフロー）は変わらず、シードとポリシー
（データ）だけが変わる — これが §1.2「構造優先」の検算である。
