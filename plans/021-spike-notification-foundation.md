## Why this matters

顧客が注文の進行を知る手段は pull 型（`trackOrder` / プロフィール注文履歴）のみで、
**「状態が変わったら知らせる」基盤がアプリに存在しない**（Notification モデルなし・
メール送信ライブラリなし。Clerk のメールは認証系のみ）。一方で、通知を必要とする機能が
複数計画中である: spike 016 の審査合否、plan 018 の RMA 状態遷移、DIRECTION-03 の
チケット返信、既存の注文状態遷移。基盤なしに各機能が個別にメール送信を実装すると、
発火点・テンプレート・opt-out 管理が散乱し、後から統合するコストが機能数に比例して増える。
本 spike は **(a) Notification テーブル（アプリ内通知の SSOT）、(b) チャネル抽象
（in-app 必須 + email はプロバイダ差し替え可能な seam）、(c) イベント → 通知マッピングの
データ化** を、最初の消費者（016/018）が「行を足すだけ」で使える形で設計する。

### 実行環境の制約

- **デプロイ先は未確定**。特定ベンダーを前提に設計しないこと。制約として扱うのは
  ベンダー名ではなく**実行モデル**であり、design doc には「どの実行モデルを仮定するか」
  を明記した上で、仮定が崩れた場合の影響範囲も書くこと:
  - **サーバーレス／リクエストスコープ実行**（Vercel・Cloudflare Workers・AWS Lambda 等）:
    常駐ワーカー不可。遅延送信は cron 相当（Vercel Cron / Cloudflare Cron Triggers /
    EventBridge 等）か送信時 inline かの選択になる。
  - **常駐プロセス実行**（コンテナ／VM。本リポジトリには `make setup` の Docker 開発
    環境が既にある）: ワーカープロセスや常駐キュー consumer が使えるため、Outbox +
    ポーリングの選択肢が広がる。
  - 設計は**サーバーレス制約を満たす側に寄せる**（より制約が強く、常駐環境でもそのまま
    動くため）。ただし「常駐ワーカー不可」を*事実*として断定しないこと — それは
    デプロイ先が決まって初めて確定する。

  > 実行環境をベンダー名で固定しない方針は
  > [`docs/architecture/rate-limiting-spike.md`](../docs/architecture/rate-limiting-spike.md)
  > と同じ（あちらは XFF 抽出規則をホスト別の表で扱う）。
- webhook 検証は Svix（`src/app/api/webhooks/`）— 外部プロバイダの配信イベント
  （bounce 等）を受ける場合の既存パターン

### 遵守すべきリポジトリ規約

- 外部呼び出し（メールプロバイダ）は `try/catch` + 構造化ログ
  （`"[Module:Function] msg", { error, stack }` の2引数形式 — `src/queries/paypal.ts` が実装例）
- **永続化（Notification/Outbox 行の書き込み）の失敗ハンドリングも定義すること** — 下記は
  外部**送信**の失敗を扱うが、行の**永続化**が失敗した場合（送信すべき通知が記録されない）の
  扱いは別問題。主処理 tx 内で書くなら tx ロールバックに巻き込まれ、tx 外なら記録漏れが起きうる。
  どちらのモデルでも「永続化失敗時に通知が黙って消えない」保証を design doc に明記する。
- **通知の「送信」失敗が主処理（注文更新等）を失敗させないこと** — 送信（外部発火）は主処理の
  `$transaction` の**外**で行う。
  > **この制約は「送信」失敗に限る。「記録（Notification/Outbox 行の書き込み）」失敗は対象外。**
  > 両者を混同すると Q4 の軸 2 の (P1)（原子的 Outbox = 同一 tx）と (P3)（記録できなければ
  > 主処理を失敗させる）が本項に抵触して読め、**採用可能な選択肢が一つも残らなくなる**。
  > 外部プロバイダの停止で注文が失敗してはならない（＝送信）が、記録漏れのまま注文だけ
  > 成立させないために主処理を巻き込むのは**意図された設計**（＝記録）である。実行モデル（commit 後 inline 発火 / Outbox）は Q4 で確定するが、
  **この tx 境界の決定は `plans/018`（RMA）Q6 の通知原子性モデルと統一すること**（両 spike で
  同じモデルを採り矛盾させない。片方が Outbox を選ぶなら他方も整合させ、相互参照を design doc に書く）
- 認可は auth-guards / サーバーアクションは `src/queries/` 配置
- スキーマ変更時は ERD 再生成（`.claude/rules/03-data-model-diagram-sync.md`）
- 外部依存の追加（メールプロバイダ SDK）は事前確認が必要な変更（ユーザー承認事項 —
  後続実装プランに明記する）

## Open questions（spike が証拠付きで必ず答える）

1. **Notification テーブルの形 + 冪等性・重複排除**: 受信者（userId）・種別・タイトル/本文
   （or テンプレートキー + パラメータ JSON）・リンク先・isRead/readAt（`Message` パターン踏襲）・
   発生源参照（orderId 等のポリモーフィック参照をどう持つか）。
   保持期間・既読一括化・ページングの要件も確定する。

   > **通知イベントの冪等性・重複排除を必須設計項目にすること**（同一イベントの再処理・リトライ・
   > webhook 再送で通知が**行として**二重に作られるのを防ぐ）:
   > - 各通知に **冪等性キー**を持たせる（例: `dedupeKey = hash(eventType + sourceRef + recipientId + 状態遷移識別子)`）。
   >   Notification（および Outbox を採るなら Outbox 行）に一意制約を張り、
   >   二重挿入を DB レベルで弾く（upsert or `ON CONFLICT DO NOTHING`）。
   >
   >   **記法**: 単一カラムなのでフィールド属性 `dedupeKey String @unique` を使う。
   >   `@@unique(dedupeKey)` は Prisma スキーマとして**不正**（ブロック属性
   >   `@@unique` は配列を取るため `@@unique([dedupeKey])`）。複合キーに拡張する
   >   可能性があるなら最初から `@@unique([...])` 形で書く。
   >
   >   **`dedupeKey` は `String`（NOT NULL）にすること。** nullable にすると
   >   PostgreSQL は NULL 同士を「区別される」と扱うため、キーが埋まらなかった
   >   通知は何件でも一意制約を通り抜け、**制約が存在しないのと同じ**になる
   >   —— まさにこの節が防ごうとしている「行としての二重作成」がキー欠落時だけ
   >   素通しになる。キーを生成できないイベントは投入前に弾くこと
   >   （plan 018 の `idempotencyKey`・plan 013 のルート一意性と同じ NULL の穴）。
   > - 送信側は **at-least-once 前提**で組む。ここで保証されるのは「行が二重に作られない」ことまでで、
   >   **外部送信が 1 回に収まることは保証されない**（理由と選択肢は下記「`dedupeKey` は
   >   『行の重複』を防ぐだけ」を参照）。外部送信の配信契約はそこで**どちらか一方を選んで**確定させる。
   >   webhook（bounce 等）受信も冪等化する。
   >
   > **「送信済み」は外部送信の前に記録しないこと**。送る前に送信済みフラグを立てると、
   > 送信が失敗した場合・プロセスがその隙に落ちた場合に、**送っていないのに送信済みと記録された
   > 通知が永久に再送されない**（サイレントロス）。これは at-most-once の挙動であり、直上で
   > 前提に置いた **at-least-once と矛盾する**（at-least-once は「重複しても失わない」保証）。
   > 記録の順序は Q4（軸 1: 送信の実行モデル × 軸 2: 通知行の永続化方式）と一体で決めること。選択肢:
   > - **送信後に記録**: 送信成功を確認してから `sentAt` を書く。プロセスが送信直後・記録前に
   >   落ちると再送される。
   >
   > **`dedupeKey` は「行の重複」を防ぐだけで、「送信の重複」は防がない。**
   > `@@unique(dedupeKey)` が保証するのは Notification / Outbox の**行が二重に作られない**
   > ことだけである。外部送信が成功した後・`sentAt` を書く前にプロセスが落ちた場合、
   > 再試行は**同じ行**を処理して**同じメールをもう一度送る** — 行は 1 つのままなので
   > unique 制約は何も検知しない。受信者の受信箱には 2 通届く。
   >
   > したがって design doc は、**外部送信そのものの重複排除をどこが担うのか**を
   > 明示的に決めること。取りうるのは次の 2 つだけで、どちらかを選んで書く:
   >
   > 1. **プロバイダの冪等性キーに委ねる**。送信 API が永続的な idempotency key を
   >    受け付け、再送時に新規送信せず元の結果を返すことを**実際に確認する**
   >    （ベンダー文書で「サポートしている」ことと「保持期間がリトライ窓より長い」ことの
   >    両方。保持期間が短ければクラッシュ復旧が窓を越えた時点で二重送信に戻る）。
   >    確認できた場合のみ「重複送信なし」を配信契約として名乗れる。
   > 2. **重複を許容する at-least-once として明記する**。プロバイダが保証しない場合、
   >    「稀に同一通知が二重に届きうる」ことを**受け入れた契約として design doc に書く**。
   >    その上で影響を減らす手当（送信直前の `attemptCount` 記録でクラッシュ再開を検知可能に
   >    する、ユーザー影響の大きい通知種別のみリース窓を短くする 等）を設計する。
   >
   > **やってはいけないのは、`dedupeKey` があるから重複送信は起きない、と書くこと。**
   > 実際には成立しない保証を design doc に書くと、後続の実装プランがそれを前提に
   > 検証を省く。
   > - **リース方式（claim → 送信 → 完了）**: 送信前に書くのは「送信済み」ではなく
   >   **`in-flight`（処理中）の確保**（`attemptCount` + `leaseExpiresAt`）に留め、送信成功後に
   >   `sentAt` を書く。リース期限切れの行は別ワーカーが再試行できるため、クラッシュしても失われない。
   >   Q4 の軸 1 で **(B) 遅延ワーカー送信**を採る場合はこちらが自然。
   >
   > いずれの方式でも、**「送信していないのに送信済みになる」状態が発生しない**ことを不変条件として
   > design doc に明記すること。
   > - 018 RMA / 016 審査など複数 spike の発火イベントが同じ規約でキーを作れるよう、
   >   dedupeKey の生成規則を本 spike で共通定義する。
2. **チャネル抽象の seam**: `sendNotification(event, recipient)` 相当の単一入口が
   in-app 記録と email 送信へ分配する形。email プロバイダを差し替え可能にする
   インターフェイス（spike 017 の `getRelatedProducts(strategy)` seam と同じ発想）を定義する。
   **in-app は必須・email はイベント種別ごとに opt-in** という初期方針の妥当性を検証する。
3. **メールプロバイダ選定（ADR）**: Resend / SendGrid / AWS SES 等を、無料枠・Next.js
   親和性・テンプレート管理・bounce webhook・ベンダーロックインの観点で比較し、
   第一候補を決める（**実装プランでの導入はユーザー承認事項**と明記）。
   ローカル/CI では実送信しないスタブ（env による無効化）を設計に含める。
4. **送信の実行モデル × 通知行の永続化方式（直交する 2 軸として決める）**:
   この項は以前 `(a) inline` / `(b) Outbox` と「必須制約 1〜3」を同一の選択肢列として
   並べていた。両者は**別の軸**であり（前者は *いつ送るか*、後者は *記録をどう失わないか*）、
   混載していると「(b) Outbox」と「制約 1: 原子的 Outbox」が同一物に見え、
   「inline + 原子的 Outbox」という成立する組み合わせが矛盾として読めてしまう。
   軸を分けて、それぞれ独立に決めること。

   **軸 1 — 外部送信の実行モデル（いつ送るか）**
   - **(A) inline 送信**: 主処理の `$transaction` の**外**・同一リクエスト内で送る。
   - **(B) 遅延ワーカー送信**: 永続化済みの行を cron / worker が後から拾って送る。

   **軸 2 — 通知行の永続化方式（記録をどう失わないか）**
   - **(P1) 原子的 Outbox**: 通知行の書き込みを主処理と同一 `$transaction` に入れ、
     主処理と生死を共にする。
   - **(P2) 再試行可能な永続キュー**: 書き込み失敗が失われないよう、再試行・DLQ を持つ
     永続キューへ投入する。
   - **(P3) 主処理を失敗させる契約**: 通知行を記録できないなら主処理自体を失敗
     （ロールバック）させ、「成立したのに通知記録が無い」状態を作らない。
   - **(P0) ログのみ**: 書き込み失敗をログ出力だけで済ませる。**排除済み**（下記）。

   **組み合わせ表**（成立する組み合わせは軸 1 × 軸 2 の積から P0 列を除いた全て）:

   | | (P1) 原子的 Outbox | (P2) 永続キュー | (P3) 主処理を失敗させる | (P0) ログのみ |
   |---|---|---|---|---|
   | **(A) inline 送信** | ✅ 成立（条件付き ※1） | ✅ 成立（条件付き ※1） | ✅ 成立（条件付き ※1） | ❌ 排除済み（= 旧「素の (a)」） |
   | **(B) 遅延ワーカー** | ✅ 成立（最も素直） | ✅ 成立 | ❌ 成立しない（※2） | ❌ 排除済み |

   旧記述の「(b) Outbox テーブル + cron 再送」が指していたのは **(B) × (P1)** の一点で、
   Outbox という語が軸 1 と軸 2 の両方に現れていたのが混載の原因。**(A) × (P1)**
   （行は主処理 tx 内に書き、送信だけ tx 後の同一リクエストで行う）は矛盾ではなく、
   inline を採るときの既定形 —— ただし**無条件には成立しない**（※1）。

   > **※1 — (A) inline の成立条件: 送信失敗の再試行経路。**
   > 軸 2 が保証するのは「**行が失われないこと**」であって「**届くこと**」ではない。
   > (A) inline はリクエスト内で 1 回送って終わりであり、**送信失敗（プロバイダの 5xx /
   > タイムアウト / 一時的なレート制限）に対する再試行経路を持たない**。したがって
   > (A) を採ると、どの軸 2 と組んでも「**通知行は残っているのに配信されていない**」状態が
   > 定常的に発生しうる。この状態は軸 2 の観点では正常（記録は原子的に残っている）なので、
   > **軸 2 だけを強化しても検出も回復もできない**。この欠落は軸 1 の (A) 自体に由来するため、
   > (A) の行**全体**に掛かる。
   >
   > (A) を初期実装に採る場合、design doc は次の (i)(ii) の**いずれか**を明示的に選ぶこと:
   >
   > - **(i) 未送信行を拾う sweeper を持つ**: 送信状態（`sentAt` / `attempts` / `lastError` 等）を
   >   行に持たせ、未送信・失敗行を後から拾って再送する経路を用意する。ただしこれは
   >   **実質的に (B) 遅延ワーカーの併用**であり、「(A) 単独」ではなくなる点を design doc に
   >   書くこと（cron の実行手段も (B) と同じ判断が要る）。
   > - **(ii) 「記録が権威・配信は best-effort」と明記する**: 再送経路を持たないことを
   >   **意図的な選択**として design doc の**障害挙動表**に書き、通知が届かないことを前提に
   >   運用する（例: 通知は補助であり、権威的な状態は常に画面から参照できる）。
   >   この場合、通知の到達を前提にした機能（「メールのリンクからしか辿れない操作」等）を
   >   設計に入れないことが制約として付く。
   >
   > (P2) 永続キューを選ぶ場合でも、**そのキューの consumer が再送を駆動するなら
   > それは (B) である**。(A) のまま (P2) を使う（＝キューは記録の保全のみに使い、
   > 送信はリクエスト内で完結させる）構成では ※1 は解消しない。
   >
   > ---
   >
   > **※2 — (B) × (P3) は成立しない: ロールバックする対象が存在しない。**
   > (P3) の契約は「通知行を記録できないなら**主処理を失敗させる**」であり、
   > 主処理がまだ commit していないことに依存する。一方 (B) 遅延ワーカーは
   > **記録が主処理の後に来る**実行モデルなので、記録が失敗した時点で主処理は
   > 既に commit 済み —— 巻き戻す対象が無く、契約を履行できない。
   >
   > 「では記録を主処理と同じ tx に入れればよい」と言った瞬間、それは
   > **(P1) 原子的 Outbox そのもの**になる。つまり (B) 行における (P3) は
   > 独立した永続化方式ではなく、成立させようとすると必ず (P1) に吸収される。
   > **(B) を採るなら選択肢は (P1) か (P2) の 2 つ**であり、この表から (P3) 列は落ちる。
   >
   > (A) × (P3) が成立するのは、inline 送信では記録と主処理が**同一リクエスト内**にあり、
   > 記録の失敗を主処理の commit 前に観測できるため。同じ (P3) でも軸 1 の値によって
   > 成立可否が変わるのはこの一点に尽きる。

   どの組み合わせを初期実装にするかは、
   **「実行環境の制約」§ と同じ前提で判断すること** —— デプロイ先は未確定なので、
   ベンダー名ではなく**実行モデル**を制約として扱う:
   - **サーバーレス／リクエストスコープ実行**: リクエスト単位の実行時間上限があり、
     常駐ワーカーを置けない。inline 送信は主処理のレスポンスを待たせ、上限に当たれば
     途中で切られる。遅延送信は cron 相当のスケジューラを外から叩く形になる。
   - **常駐プロセス実行**: 実行時間上限が無く worker/consumer を常駐できるため、
     Outbox のポーリング再送が素直に組める。
   - 「サーバーレス制約を満たす側に寄せる」原則（同 §）に従い、**両モデルで成立する案**を
     選ぶ。特定ベンダーの実行時間制約を根拠に据えないこと。
   Outbox を選ぶ場合は cron の実行手段も決めるが、これも実行モデル別に書く
   （プラットフォーム提供の cron / 常駐スケジューラ / 外部スケジューラ、の選択肢として）。

   > **永続化（Notification/Outbox 行の *書き込み*）失敗の扱いも Q4 と一体で決めること**
   > （「遵守すべきリポジトリ規約」§ の該当項目を設計判断に昇格）。外部**送信**の失敗と、
   > 送るべき通知の**行が記録されない**失敗は別問題。主処理 tx 内で書くなら tx ロールバックに
   > 巻き込まれ、tx 外なら記録漏れが起きうる。選んだ組み合わせ（軸 1 × 軸 2）で
   > **「永続化失敗時に通知が黙って消えない」不変条件がどう成立するか**を、障害挙動表
   > （プロバイダ停止・タイムアウト・部分失敗に加え **行書き込み失敗**の列）に明記する。
   >
   > **（必須制約）軸 2 に (P0) ログのみ を選ぶことはできない。** 主処理 tx の
   > **外**で Notification/Outbox 行の書き込みが失敗した場合、ログだけでは通知を復旧できない
   > （記録が消える）。Q4 の完了条件は「軸 2 が (P1)/(P2)/(P3) のいずれかであること」——
   > ただし **(B) 遅延ワーカーを選んだ場合は (P1)/(P2) の 2 択**になる（(B) × (P3) は
   > 成立しない。組み合わせ表の ※2 を参照）。
   >
   > **ただし (P2) を選んだだけでは不変条件は満たされない。** (P2) 永続キューは
   > **enqueue 自体が主処理 tx の外**で行われるため、enqueue が失敗すると通知行はどこにも
   > 残らず、排除したはずの (P0) と同じ「黙って消える」に落ちる（キューが永続なのは
   > *enqueue が成功した後*の話であり、enqueue の失敗そのものは守ってくれない）。
   > (P2) を選ぶ場合は次のいずれかを満たすこと:
   > - **(P2-a)** enqueue が主処理 tx とアトミック（例: tx 内で Outbox 行を書き、
   >   コミット後にその行からキューへ送る = 実質 (P1) との併用）、**または**
   > - **(P2-b)** enqueue 失敗時の復旧経路を**障害挙動表の「行書き込み失敗」列に明記**する
   >   （何を以て失敗を検知し、どこから再構成するか。「ログに出す」だけでは (P0) と同値なので不可）。
   >
   > design doc に (P2) とだけ書いて完了扱いにしないこと。
   >
   > **(P1) と (P3) は「遵守すべきリポジトリ規約」§ の「通知の『送信』失敗が主処理を
   > 失敗させないこと」と衝突しない。** 同項は**送信**（= 軸 1）に限った制約であり、
   > **記録**（= 軸 2、行の書き込み）の失敗で主処理を巻き込むことは本項が意図して許している。
   > design doc では両者を必ず別の失敗モードとして扱い、障害挙動表でも列を分けること
   > （混同すると「規約に反するから (P1) も (P3) も採れない」となり、残る (P2) だけが
   > 唯一の選択肢であるかのように読めてしまう）。
   >
   > 組み合わせ表を書き写すときは **(P0) 列が排除済みである**ことを落とさないこと ——
   > 排除済みの案が選択肢一覧に残っていると、実装プランが「(A) inline 送信 + 行の書き込み
   > 失敗はログのみ」（= 旧「素の (a)」）を「plan で認められた選択肢」として採用しうる。
5. **イベント → 通知マッピングのデータ化**: どのイベントで・どのロールに・どのチャネルで
   送るかを、コード内定数（型安全・レビュー可能）とするか DB テーブル（無停止変更可能）と
   するか。ブランド未定の「ポリシー差し替え」原則との整合を根拠に確定し、
   初期マッピング表（少なくとも: 注文 Shipped/Delivered、店舗承認、016 審査合否、
   018 RMA 主要遷移）を書く。
6. **ユーザーの通知設定（opt-out）**: email のカテゴリ別 opt-out を初期スコープに
   含めるか。含めない場合も、法令上 opt-out 必須になりうるカテゴリ（販促系）を
   トランザクショナル通知と分離しておく設計上の線引きを書く。

## STOP conditions

以下の場合は STOP して報告する:

- Notification 系モデルまたはメール送信ライブラリが既に追加されている（前提消滅）
- 選定候補のプロバイダがすべて「サーバーレスからの同期送信」に実用上の問題（レイテンシ・
  レート制限）を抱えると判明し、Outbox + cron が必須になるのに、**想定するどの実行モデルでも
  スケジューラを確保できない**と判明した場合（プラットフォーム提供 cron も常駐スケジューラも
  使えない）— 代替（外部キューサービス等）はスコープ拡大のため判断を仰ぐ
- 016/018 の spike が実行済みで、その通知要件が本 spike のマッピング形式で表現できない
  場合 — 形式の拡張案を添えて報告する
